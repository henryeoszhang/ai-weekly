# AI WEEKLY

個人制作の日本語AI週報（試行版）。AIを用いて公開資料を整理・要約し、経営・管理職、一般社員、開発者向けの3版に編集しています。各社・団体の公式媒体ではありません。

## 掲載構成

- `index.html`: 最新号への入口と発行一覧
- `issues/YYYY-MM-DD/index.html`: 各号の固定ページ
- `issues/YYYY-MM-DD/executive.html`: 経営・管理職版
- `issues/YYYY-MM-DD/employee.html`: 一般社員版
- `issues/YYYY-MM-DD/developer.html`: 開発者版

各版は自立した静的HTMLです。ビルド、JavaScript、外部フォント、解析タグ、第三者の埋め込みは不要です。`.nojekyll` は静的ファイルをそのまま配信するための設定です。

## GitHub Pagesへの週次投稿手順

この節は、検証済みの3版が完成してから公開確認・完了連絡までの手順です。手動更新と自動制作後の更新で共通して使用します。毎回、作業開始時に最新の `main` とこのREADMEを読みます。記事の選定・採点・順位・出典・留保は、公開処理の都合で変更しません。

### 1. 公開先と入力を確認する

- リポジトリ: [henryeoszhang/ai-weekly](https://github.com/henryeoszhang/ai-weekly)
- 公開トップ: [AI WEEKLY](https://henryeoszhang.github.io/ai-weekly/)
- 配信元: `main` ブランチの `/ (root)`。`.nojekyll` を維持します。
- 入力: 完成・検証済みの経営・管理職版、一般社員版、開発者版の3HTML、発行日、対象期間、締切、記事数・コラム数、実施済み検査と未確認事項。
- 発行日は日本時間の `YYYY-MM-DD`。通常の対象期間は前週月曜00:00から発行日月曜00:00直前までです。
- 現在の `main` のコミットID、トップの最新号と過去号一覧、同じ発行日のフォルダの有無を確認します。接続や書き込み権限がなくなっていたら停止し、新しい認証情報や権限変更で迂回しません。

### 2. 固定URLの号を準備する

公開専用の作業場所で、次の4ファイルを用意します。

```text
issues/YYYY-MM-DD/index.html
issues/YYYY-MM-DD/executive.html
issues/YYYY-MM-DD/employee.html
issues/YYYY-MM-DD/developer.html
```

号の `index.html` に3版への相対リンク、発行日、対象期間、締切、実数を簡潔に載せます。読者の判断に影響する留保は、該当記事の近くに残します。3版の本文・順位・点数・出典・読者に必要な注記を保持し、制作管理用の情報、認証情報、非公開情報、不要な個人情報は公開ファイルに含めません。HTMLコメント、属性、隠し要素、リンク先も確認します。権利や公開可否に未解消の問題があるものは公開しません。

公開ページには「今号の確認範囲」、候補件数、調査・監査の進行状況、順位安定性の未確認、表示・印刷検査の未実施など、制作・品質管理の説明を載せません。必要な制作記録と検査結果は非公開の作業記録や依頼者への連絡に残します。出典リンク、対象期間、提供条件、研究段階、企業側の主張であること、SNSの発言者・コミュニティ・反応期間など、記事の意味や判断に関わる事実上の留保は保持します。AIを用いた制作であることは短い一文で示します。この整理は公開用コピーに限り、ニュースの採否・順位・点数・根拠を変更しません。

同じ発行日のフォルダが既にある場合、再実行か訂正かを先に判断します。同一内容なら二重登録せず、配信状況を確認します。内容が異なる場合は既刊の訂正として扱い、説明なしに上書きしません。

### 3. 各版の色にパーツを合わせる

色の正本は、その号の `executive.html`、`employee.html`、`developer.html` です。各HTMLのCSSを確認し、後から上書きされた定義も含む最終的な `--accent` と `--tint` を取得します。先頭の共通 `:root` だけを読んだり、版名から色を推測したりしません。

トップと号の入口の各カードに `data-edition="executive"`、`data-edition="employee"`、`data-edition="developer"` を設定し、それぞれの範囲へ該当版の色変数を反映します。カードの上線、用途の小見出し、「読む」ボタン、キーボードフォーカス、過去号一覧の読者版リンクも対応する版の色で揃えます。背景色を使うパーツには、その版の `--tint` を使います。過去号リンクはリンク先の号に対応する色を保持します。

2026年10月5日号の実HTMLで確認した配色は次の通りです。これは当該号の確認値であり、次号は再取得します。

- 経営・管理職版: `--accent: #654397`、`--tint: #ece6f4`
- 一般社員版: `--accent: #2f6b4d`、`--tint: #e4eee4`
- 開発者版: `--accent: #285f87`、`--tint: #e1ecf3`

### 4. 最新号と過去号一覧を更新する

トップ `index.html` の最新号リンクを新しい固定日付パスに切り替え、発行日・期間・実数を更新し、読者に必要な留保だけを適切な位置に残します。`#archive` の先頭に新号を1件追加し、旧号の「最新号」表示を外します。以前の号のHTML、一覧項目、固定URLは残します。既存の過去号を新号の内容で上書きしません。

### 5. 公開前に点検する

- [ ] 通常は各版20件のニュースと独立した「先週の話題・議論」があり、実数が入口の表示と一致する。承認された条件付き納品は実数・不足理由をそのまま示す。
- [ ] 3版の発行日、対象期間、締切、出典、見出し、目次アンカー、留保に食い違いがない。
- [ ] トップ、号の入口、3版、過去号の相対リンクとページ内リンクが切れていない。
- [ ] 各カード・ボタン・版リンクの色が、対応する号の実HTMLの最終色と一致する。
- [ ] 本文と属性・コメント・リンクを含め、公開できない情報や不要な個人情報が混入していない。
- [ ] PCとスマートフォン幅で折り返し、はみ出し、ボタン、フォーカスを確認する。印刷表示も確認する。未実施の検査を完了と書かない。
- [ ] 差分は新号4HTMLとトップ `index.html` の計5パスだけ。通常の週次追加でREADME、設定、過去号を変更しない。手順や既刊の変更は別途依頼された範囲だけに限定する。

必要な内容・安全点検を通過していない未完成物は公開しません。構造チェックだけで記事の事実確認や表示確認を済ませたことにしません。

### 6. 変更を一つのコミットで反映する

反映直前に `main` の最新コミットを再確認します。他の更新が入っていたら読み直して変更を取り込み、他の作業を消さないようにします。原則として上記5パスを一つのコミットで追加・更新します。作業フォルダ全体を一括追加せず、許可されたパスを明示します。コミットメッセージには発行日を含めます。force pushは使用しません。

既存のGitHub連携、または認証済みの通常のGit操作を使います。新しいサービス登録、トークン発行、Pages設定変更は週次更新に必要ありません。反映後は、意図したコミットがリモートの `main` に存在することを確認します。

### 7. 配信完了と公開ページを確認する

[Actions](https://github.com/henryeoszhang/ai-weekly/actions) で、今回のコミットIDに対応する `pages build and deployment` のビルド・配信が成功するまで確認します。別の古い実行の成功で代用しません。コミット成功だけでは公開完了と判定しません。

配信後、次の5ページを実際に開き、期待する発行日・本文・色・リンクが反映されていることを確認します。

1. トップ `https://henryeoszhang.github.io/ai-weekly/`
2. 号の入口 `https://henryeoszhang.github.io/ai-weekly/issues/YYYY-MM-DD/index.html`
3. 同じフォルダの `executive.html`
4. 同じフォルダの `employee.html`
5. 同じフォルダの `developer.html`

トップの最新号から3版に移動できること、号の入口からトップへ戻れること、過去号一覧から以前の号を開けることも確認します。GitHub側の反映には時間がかかる場合があります。[配信元の設定と動作](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site) と [公開後の確認](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site) はGitHub公式手順を参照してください。

### 8. 結果を連絡する・失敗を扱う

公開成功の連絡にはトップURL、当該号の固定URL、3版が公開済みであることを含めます。元の3HTMLのファイル納品も継続します。作業記録には発行日、反映コミット、配信実行URL、確認したページ・表示範囲、残る留保を記録します。

ビルド・配信が失敗したら今回の実行ログを確認し、認められた範囲で修正します。進行中・未確認・権限不足を成功と報告しません。解決できない場合は、ファイル完成、GitHubへの反映、公開確認のどこまで済んだかを分けて連絡し、検証済みのHTMLは届けます。新しい権限、外部送信先、サービスへの切り替えは勝手に行いません。

## 編集と訂正

各版の「順位と点数について」に点数の読み方を簡潔に示し、各記事と「出典と編集方針」に参照資料を掲載します。点数は編集上の評価です。研究や製品の主張は、各記事に示した出典と条件の範囲で扱います。

同じ号を訂正する場合は日付の固定URLを保ち、影響する記事に訂正日と変更内容を記載します。重要な事実を、説明なしに書き換えない運用とします。引用先・参照先の文章や資料の権利は各権利者に帰属します。
